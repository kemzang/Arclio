# PDF thumbnails are rendered in the main process with a native canvas

Library thumbnails for PDFs are produced by rasterising the document's first
page in the main process, using `pdfjs-dist` driven by `@napi-rs/canvas`.
Documents previously got a flat placeholder, and every format in the `document`
media type was labelled "PDF" — including `.docx` and `.txt`.

A media library is judged on its grid. A wall of identical grey placeholders
reads as broken, so real page previews are a product requirement, not polish.

## Why a native canvas

pdf.js is a browser library: it rasterises through a DOM canvas and expects
`Path2D`, `DOMMatrix` and `ImageData` as globals. Node provides none of them.

Three options were weighed.

`sharp` was checked first, since it already ships: its prebuilt libvips reports
`format.pdf.input` as `{file: false, buffer: false, stream: false}`, so it
cannot read PDFs at all. An offscreen `BrowserWindow` would reuse Chromium's
bundled PDF engine with no new dependency, but costs a hidden window per
thumbnail and an awkward lifecycle inside a batch indexer.

`@napi-rs/canvas` was chosen. It is prebuilt per platform (no node-gyp), and it
was **already** in the dependency tree and already unpacked into the packaged
app as an optional dependency of `pdfjs-dist` — so declaring it directly adds no
new native payload to any release artifact. It is pinned to the version already
resolved there.

## Consequences

`@napi-rs/canvas` is external to the main bundle, like `better-sqlite3`: it
loads a platform-specific `.node`, which bundling would break. electron-builder
already ships `node_modules` and auto-unpacks native modules from the asar, so
the runtime bare import resolves without packaging changes.

pdf.js and the canvas binding are imported lazily, keeping ~4MB and a native
binding off the startup path — thumbnails are generated by the indexer, long
after boot. The canvas globals are installed once, on first use.

Rendering is best-effort. A corrupt, encrypted or password-protected PDF must
not fail an indexing pass, so a render failure falls back to the placeholder.

Only PDF gets a real render. The other `document` extensions (`.epub`, `.doc`,
`.docx`, `.txt`, `.rtf`, `.odt`) have no rasteriser here and fall back to a
placeholder now labelled with their own format. Extracting embedded cover art
from EPUB containers is the obvious next step, and needs no new dependency.
